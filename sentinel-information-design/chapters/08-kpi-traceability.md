# 08 · KPI Traceability — Every Element on the 48-min → 90-s Path

**Study:** FlytBase Sentinel — operator-interface information design · **Doc type:** synthesis chapter (no new research; built from chapters 01/02/03/04/05/07/09 and `repo-audit.md`) · **Compiled:** 2026-09-22

## 1 · Method

The KPI anchor is **given by the challenge brief, not re-derived**: traditional first-signal → effective response ≈ **48 min**, Sentinel target ≈ **90 s** [repo·`FlytBase_Sentinel_Project_Brief_Con.txt` §1]. `PRODUCT.md` states the provenance plainly: "the 48-minute baseline and 90-second target come from the challenge brief, not a field study." **Scope is time-to-defensible-decision** — detection → validated alert → tasking decision → supervised execution handoff — **not water-on-fire** [05 scope note]: crew turnout + travel (11–35 min) is *not compressible* by information systems [05(c)], and the 90-s clock ends decision-complete, with the operator repositioned at exactly three human gates (verify → authorize → supervise) [05(d)].

The 90-s arc is the repo-canonical handoff [repo·brief §4]: **0–15 s** sensor fusion before interrupt (thermal spike 03:47:03 → alert threshold crossed 03:47:18 → nearest drone launches autonomously) → **15–45 s** single-question VERIFY → **45–75 s** CONTAIN authorize (press-and-hold) → **75–90 s** RESCUE exception-only supervision. Arithmetic basis: 48 min = **2880 s**; 2880 ÷ 90 = **32** ⇒ **×32 compression**. Two honesty rules govern every number below. **(a) Constructed allocations:** the four segment values (15 + 30 + 30 + 15 = 90 s) are constructed allocations calibrated to the given anchor, exactly as 05(b) constructed the 48-min decomposition — they are design heuristics `[est]`, not measurements. **(b) Parallelism:** the arc is a pipeline, not a serial sum — elements marked *parallel* (dock launch 45–60 s, EO/thermal corroboration, projection precompute, audit append) ride inside the windows and are **not additive**; the only serial sum claimed is the four segment windows. Per-element "seconds saved" columns therefore overlap where several elements compress the same traditional step; only the segment total binds. Range honesty: 05(b) totals run 24–90 min, so the defensible compression ratio is **×16** (favorable 24-min case) to **×60** (unfavorable 90-min case); **×32 uses the 48-min midpoint**.

## 4 · Measurement plan

> Metric names follow brief §10 (median time-to-authorize, override rate, false-positive escalation rate); brief §10's exact target text is not quoted in the input set, so numeric targets below are design targets `[est]` pending baseline capture. All capture points are repo-native: the state machine already timestamps transitions (verified by `verify:machine` 31 transitions) and P9 already writes gate receipts with hold duration + snapshot hash [repo].

| Metric | Definition | UI capture point | Target |
|--------|------------|------------------|--------|
| **Median time-to-authorize** (brief §10) | Median wall-clock from alert interrupt (threshold crossing, `alert-surfaced`) to G2 completion receipt | P9 gate receipts (hold duration + snapshot hash); state-machine transition timestamps alert-surfaced → authorize-containment | Median ≤75 s (window bound); stretch ≤60 s `[est]` |
| **Override rate** (brief §10) | Fraction of TALON proposals/recommendations overridden by the operator via DissentGate (with reason) | DissentGate reason capture → P9 receipts; `OVERRIDE_REASONS` distribution | <10% of proposals `[est]`; trend down across tuning cycles |
| **False-positive escalation rate** (brief §10) | Fraction of escalated incidents (G1 confirmed / authority packet sent) later dismissed as false positives with a reason code | Dismissal reason codes + packet lifecycle (drafting \| ready \| sent) in P9; dismissed-alert retrievable history | ≤2% of confirmed incidents `[est]` |
| Median time-to-confirm (G1) — supporting | Alert interrupt → confirm-incident receipt | P9 receipt; state-machine timestamps | ≤45 s (inside VERIFY window) `[est]` |
| Evidence-card open latency — supporting | Interrupt/click → C1 card rendered | C1 instrumentation | ≤1 s at P95 [S17][INF] |
| Alert-to-eye latency — supporting | Threshold crossing → drone sensor-on over incident | P5 fleet status transitions (launching → on-station) → receipts | ≤60 s (Dock 2 45–60 s [R2·S8]; Dock 3 10 s [R2·S9a]) |
| Interrupt budget compliance — supporting | Interrupting (T1/T2) alarms per 10 min per console | Alert-tier event log (07 §3) | ≤2 [S28] |
| Data-age compliance at gates — supporting | % of gate completions where every unlock-checklist item passed its age-vs-requirement check (projection <5 min, obs <30 min, ADS-B <10 s) | C3 checklist state + snapshot hash in receipt | 100% — hard Class-3 requirement [repo·docs/04] |
