01 - Problem

The hardware was fast. The interface made response slow.

In a wildfire scenario, the sensor can detect the anomaly immediately and a drone can launch quickly. The slow part is the human assembling a trustworthy picture from disconnected systems under pressure.

The old workflow asked the operator to cross-reference thermal sensors, satellite imagery, municipal permits, drone readiness, and evacuation context before escalating. Each system had useful data, but no single surface explained what decision needed to happen next.

I reframed Sentinel as a decision interface, not a monitoring dashboard. TALON assembles evidence, marks conflicts, and prepares packets. Asha stays accountable for the decisions that carry public-safety risk.

Design problem

Compress detection-to-escalation without making AI look more certain than it is. The interface has to move fast and still show why the recommendation is trustworthy.

02 - Architecture

Two operating modes, one persistent map, seven supervised agents.

The portfolio-wide shell stays clean here: a plain section headline, followed by structured product evidence. The content density increases only where the design decision needs it.

Mode A - Intelligence

Before authority notification

TALON assembles the situation brief, compares sensor sources, checks municipal records, and routes the operator through a small number of high-confidence decisions.

Mode B - Operations

After authority notification

The interface reduces density. Detailed cards collapse to telemetry strips, exception alerts become the primary feed, and Asha supervises execution instead of manually directing every drone.

From thermal alert to authorized notification in 90 seconds.

TALON detects a thermal anomaly and assembles a brief before interrupting Asha. The operator is not handed raw data. She is handed the first decision.

04 - Decisions

Five decisions that make the work feel real.

This is where v5's density stays useful. Recruiters should see that the project is not just screens. Each card exposes the tradeoff, the rejected paths, and the final rule.

D-01

Limit the 90-second claim to verified escalation, not full containment.

Full containment depends on weather, ground crews, terrain, and municipal response. Verification is the part the interface can credibly improve.

A
Claim fire contained in 90 seconds
Rejected because it sounds impressive but collapses under real-world constraints.
B
Claim drone launch in 30 seconds
Rejected because it is mostly a hardware capability, not the designed operator experience.
C
Claim verified escalation in 90 seconds
Chosen because it maps directly to interface work: assemble, verify, authorize.
Tradeoff

Less flashy metric, stronger credibility in an interview conversation.

D-02

Force confirmation when sensor and permit records conflict.

AI can assemble the conflict quickly, but silently resolving it would hide the exact moment where human judgment matters.

A
Let TALON resolve permit conflicts silently
Rejected because sensor and municipal data can update at different speeds.
B
Block the map with a modal
Rejected because it removes spatial context during active size-up.
C
Lock the action bar and show the conflict inline
Chosen because Asha keeps the map, sees the issue, and confirms the resolution.
Tradeoff

One extra step protects against false authority while keeping the operator in context.

D-03

Show individual source states instead of a single confidence score.

One confidence number looks clean, but it hides why the system believes something and which source is weak.

A
Use one AI confidence score
Rejected because it overstates certainty and invites blind trust.
B
Show every raw reading
Rejected because it recreates the manual cross-reference problem.
C
Use source chips with status and freshness
Chosen because it gives accountability without flooding the screen.
Tradeoff

The UI gives up some visual minimalism to make AI reasoning inspectable.

D-04

Switch to vector coordinates when cell bandwidth drops.

Video is useful until it becomes unreliable. The interface needs a graceful fallback that still supports command decisions.

A
Keep HD video as the primary evidence
Rejected because low bandwidth can make the UI look active while data is stale.
B
Show a generic connection error
Rejected because it explains the failure but does not support the mission.
C
Drop HD and switch to LiDAR vectors
Chosen because the operator keeps usable spatial information under degraded network conditions.
Tradeoff

Less cinematic feed, more dependable operational truth.

D-05

Reduce interface density as urgency rises.

The same layout grid remains stable, but information depth changes by phase so the operator is not re-learning the interface mid-incident.

A
Use one dense dashboard for every phase
Rejected because operations mode should not read like investigation mode.
B
Use separate layouts per phase
Rejected because switching structures under stress increases reorientation cost.
C
Keep the grid, reduce content depth
Chosen because spatial memory stays stable while cognitive load drops.
Tradeoff

Less dramatic transition, more reliable operator behavior.

06 - Iteration

Two early directions I would show briefly, not bury.

For a long first-job case study, failed directions help if they are specific and short. They should prove judgment, not inflate the page.

V0.1 - Slider escalation model
Looked interactive, but made escalation feel like a subjective intensity setting.

Discarded: escalation slider

A slider was visually simple, but wrong for public-safety accountability. The final design uses explicit decisions with evidence and audit state.

V1 - Full automation scope
Compressed the wrong part of the workflow and made TALON feel over-authorized.

Corrected: automation scope

Early framing tried to make the whole incident fit the 90-second story. The stronger version limits the claim to verified escalation.

08 - Outcome

What the design achieved, and what I would test next.

This closes the case study with product maturity instead of a vague success statement. Since this is a challenge project, the outcome is framed as validation targets and review criteria.

Primary validation

Time to first decision

Measure from alert arrival to dispatch action. If this exceeds 15 seconds, the brief format is not surfacing the right information first.

Governance validation

Correct handling of blocked decisions

Review whether operators understand why a decision is blocked and whether the audit trail captures the human confirmation cleanly.

Operational validation

Recovery under degraded feeds

Test whether Asha can keep command confidence when HD video drops and the interface switches to vector or LiDAR evidence.

Cognitive-load validation

Density change without reorientation

Confirm that operators understand the shift from detailed intelligence mode to compact operations mode without losing the spatial model.

Reflection

The most important design decision was refusing to make TALON look magic. The final system is fast because it prepares the right decision, not because it removes accountability. If I had more time, I would run scenario testing with emergency dispatchers, stress-test the copy under low-light conditions, and compare the source-chip evidence model against a more compact confidence summary.
